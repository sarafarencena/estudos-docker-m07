1. O que provavelmente está sendo avaliado

Pense como uma criança montando uma cidade de LEGO. Não basta saber encaixar peças. Você precisa saber: quais casas existem, quem fala com quem, por onde passam as ruas, qual peça resolve cada problema e como provar que a cidade funciona.

O ponto central é responder perguntas como:

  • Quantos serviços existem?
  • Quem chama quem?
  • Em qual porta cada serviço escuta?
  • O que precisa estar acessível pelo computador e o que só precisa ser acessível entre containers?
  • Que recurso resolve o problema: Dockerfile, rede, Compose, volume, healthcheck, multi-stage?
  • Que teste prova que a decisão funcionou?
Regra de ouro: uma decisão técnica fica forte quando você consegue dizer problema → decisão → evidência.

2. UML — desenhar antes de construir

Explicação para 7 anos: UML é como desenhar o mapa de uma brincadeira antes de começar. Um desenho mostra quem participa, outro mostra quem conversa com quem, outro mostra onde cada coisa mora.

2.4 Componentes × implantação

Componentes

Mostra as partes lógicas do software: frontend, API, serviço de modelo, banco.

Pergunta: “Quais blocos existem e dependem de quais outros?”

Implantação

Mostra onde essas partes rodam: host, container A, container B, servidor, nuvem.

Pergunta: “Onde fisicamente/logicamente cada artefato executa?”

Pegadinha: diagrama de sequência não é para desenhar a estrutura permanente do sistema; ele é para mostrar interações ao longo do tempo. Diagrama de componentes não substitui um sequência.

3. Docker — empacotar para executar de forma previsível

Explicação para 7 anos: imagine que seu programa é um brinquedo que só funciona se tiver pilhas, peças e instruções certas. Docker coloca o brinquedo e tudo que ele precisa em uma caixa padronizada.

3.1 O fluxo que você precisa saber de cabeça

Dockerfile
→ build →
Imagem
→ run →
Container
ConceitoO que éPergunta mental
DockerfileReceita para construir uma imagem.“Como preparo o ambiente?”
BuildProcesso que lê a receita e gera a imagem.“Consegui montar o pacote?”
ImagemMolde/pacote imutável usado para criar containers.“Qual versão do pacote vou executar?”
RunAção de criar/iniciar um container a partir da imagem.“Quero executar esta imagem.”
ContainerInstância em execução da imagem, com camada gravável.“O processo está vivo?”

3.2 Como ler um Dockerfile sem decorar sintaxe

FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install -r requirements.txt
COPY . .
EXPOSE 5000
CMD ["python", "app.py"]

Leia em português:

  1. FROM: “comece de uma base que já tem Python”.
  2. WORKDIR: “trabalhe dentro desta pasta”.
  3. COPY: “leve arquivos do projeto para a imagem”.
  4. RUN: “execute algo durante o build”.
  5. EXPOSE: “documente que a aplicação escuta nessa porta”.
  6. CMD: “quando o container iniciar, execute isto”.
RUN ≠ CMD.
RUN acontece na construção da imagem.
CMD define o comando padrão quando o container é iniciado.

3.3 O que observar se receber um Flask pronto

  • Qual arquivo inicia a aplicação?
  • Quais dependências precisam ser instaladas?
  • Qual porta o Flask usa?
  • Ele escuta em 0.0.0.0 dentro do container?
  • Ele precisa chamar outro serviço? Qual URL espera?
  • Quais variáveis de ambiente existem?
  • Existe endpoint simples como /health para teste?
Pegadinha Flask: dentro de um container, escutar somente em 127.0.0.1/localhost pode impedir acesso externo ao processo. Para ser alcançável pela rede do container, o servidor normalmente precisa escutar em 0.0.0.0.

4. Multi-stage — separar “construir” de “rodar”

Analogia: para construir uma casinha você usa furadeira, serrote e escada. Depois de pronta, você não precisa morar com a furadeira e o serrote dentro da sala.
Stage 1: Builder
compilador + ferramentas
→ copia só o artefato →
Stage 2: Runtime
somente o necessário para executar

Quando usar? Quando existem ferramentas necessárias apenas para gerar o artefato final, como compiladores, Node para construir um frontend ou dependências de build.

Benefícios:

  • imagem final menor;
  • menos componentes desnecessários;
  • menor superfície de ataque;
  • deploy e transferência mais leves.
Pegadinha: multi-stage fica no Dockerfile, não no Compose. O Compose coordena serviços; o multi-stage define como uma imagem é construída.

5. Compose, redes e comunicação entre serviços

Analogia: Dockerfile ensina a construir cada casa. Docker Compose desenha o condomínio: quais casas existem, quais ruas conectam elas, quais portas ficam abertas e quais dependem de outras.

5.4 depends_on × healthcheck

depends_on organiza a inicialização, mas iniciar o container não significa que a aplicação já está pronta.

Se você precisa esperar o serviço realmente responder, combine a dependência com um healthcheck.

Container “started”

O processo do container foi iniciado.

Serviço “healthy”

Um teste definido confirmou que a aplicação está respondendo corretamente.

5.5 Como provar que um serviço fala com o outro

O professor disse que a forma de teste pode ser livre. Então escolha uma evidência simples e explicável.

  1. Suba a aplicação.
  2. Confirme que os containers estão rodando.
  3. Faça A chamar B pela rede interna usando o nome de B.
  4. Registre a resposta e o status HTTP.
  5. Explique o que a evidência prova.

Ferramentas possíveis: curl, Postman, Insomnia, Thunder Client, HTTPie ou um teste simples em Python.

O teste mais convincente: uma rota de A chama uma rota de B e devolve o resultado. Assim você prova não apenas que A está vivo, mas que A consegue resolver o nome de B, abrir conexão e receber uma resposta.

5.6 Volumes — quando os dados precisam sobreviver

Container é descartável. Se os dados precisam sobreviver à recriação do container, use armazenamento persistente.

RecursoUso
VolumeDados gerenciados pelo Docker; comum para bancos.
Bind mountMapeia uma pasta do computador para dentro do container; útil em desenvolvimento.
tmpfsMemória temporária; some ao parar.

7. MLOps — manter ML confiável depois do “funcionou na minha máquina”

Explicação para 7 anos: treinar um modelo é como ensinar um cachorro um truque. MLOps é cuidar para que você saiba qual cachorro foi treinado, com qual treino, quais regras foram usadas, se ele ainda faz o truque e o que fazer se ele começar a errar.

7.1 Docker ajuda MLOps, mas não é MLOps inteiro

Docker ajuda principalmente na reprodutibilidade do ambiente e empacotamento. MLOps cobre o ciclo de vida do sistema de ML.

Dados
→
Pré-processamento
→
Treino
→
Modelo
→
Deploy
→

7.2 Reprodutibilidade

Significa conseguir recriar um resultado sabendo quais elementos produziram aquele modelo:

  • versão dos dados;
  • código;
  • features e pré-processamento;
  • hiperparâmetros;
  • dependências;
  • modelo resultante.

7.3 Versionar modelo sem versionar pré-processamento é perigoso

O modelo aprendeu a trabalhar com uma representação específica. Se o scaler, encoder, ordem das features ou regras de transformação mudam, o mesmo modelo pode receber entradas diferentes das usadas no treino.

Portanto, pense no deploy como um pipeline:

entrada bruta → validação → transformação/encoding/scaling → modelo → pós-processamento → resposta

7.4 Rastreabilidade

Pergunta-chave: “De onde veio este modelo?”

Você deveria conseguir associar um modelo a experimento, métricas, dados, código, configuração e artefatos.

7.5 Monitoramento

O modelo pode estar tecnicamente online e ainda assim estar ruim. Monitore duas famílias de sinais:

Sistema

latência, erros, disponibilidade, CPU/memória, filas.

Modelo/dados

distribuição das entradas, qualidade da previsão, drift, taxa de confiança, métricas quando o rótulo chega.

7.6 Drift

TipoO que mudou?Exemplo
Data driftA distribuição de X mudou.Transações passaram a ter valores muito maiores.
Concept driftA relação X → Y mudou.Um padrão que antes indicava fraude agora é comportamento normal.
Pegadinha: retreinar não é automaticamente a primeira resposta. Primeiro detecte, investigue e confirme o problema. A degradação pode vir de dado quebrado, mudança de schema, bug de pré-processamento, latência, mudança de população ou concept drift.

7.7 CI/CD em uma frase

CI: integrar mudanças e validar automaticamente com testes/builds. CD: levar uma versão validada até ambientes de execução de forma controlada.

Em MLOps, o pipeline pode incluir testes de dados, pré-processamento, modelo, imagem Docker, integração entre serviços e critérios antes do deploy.

8. Como explicar no README com suas próprias palavras

Seu README deve mostrar compreensão, não apenas listar comandos.

Estrutura simples

  1. Problema: o que precisava funcionar?
  2. Arquitetura: quais serviços existem e quem chama quem?
  3. Decisões: por que Dockerfile, Compose, rede, porta, volume, multi-stage etc.?
  4. Execução: como a solução é construída e iniciada?
  5. Teste: qual teste foi feito e o que ele prova?
  6. Limitações: o que ainda não está coberto?

Modelo de raciocínio

Problema: o backend precisava chamar o serviço de estoque.
Decisão: coloquei ambos na mesma rede do Compose e usei o nome do serviço como hostname.
Evidência: uma requisição feita pelo backend ao endpoint /health do estoque retornou HTTP 200.
Conclusão: a resolução de nome e a comunicação HTTP entre os serviços funcionaram.
Fraco: “Usei Docker Compose porque era necessário.”

Forte: “Usei Compose porque a aplicação possui múltiplos serviços que precisam subir com configuração de rede e variáveis de ambiente consistentes; ele centraliza essa orquestração local.”

10. Pegadinhas que valem revisão

  • Imagem ≠ container: imagem é o molde; container é uma instância em execução.
  • EXPOSE não publica porta: quem publica é -p ou ports.
  • HOST:CONTAINER: 8080:80 não significa o contrário.
  • localhost dentro de A é A: para chegar em B, use o nome do serviço na rede.
  • depends_on não garante “pronto”: para readiness, use healthcheck/condição adequada.
  • RUN ≠ CMD: build versus inicialização do container.
  • Multi-stage ≠ Compose: um otimiza a construção da imagem; o outro coordena serviços.
  • Volume ≠ imagem: dados persistentes não devem depender da camada descartável do container.
  • Docker ≠ MLOps completo: ele resolve parte do empacotamento/reprodutibilidade.
  • Modelo versionado sozinho não basta: pré-processamento e schema precisam estar alinhados.
  • Data drift ≠ concept drift: mudou X versus mudou a relação X→Y.
  • Diagrama de sequência ≠ componentes: tempo/interação versus estrutura.
  • Teste “container está Up” ≠ teste funcional: prove a comunicação ou comportamento esperado.

11. Autoavaliação — responda antes de abrir

1. Você recebe frontend + Flask API + banco. Qual seria sua primeira ação?
Entender a arquitetura: quantos serviços existem, portas, dependências, fluxo de chamadas, variáveis e o que precisa ser acessível externamente. Só depois escrever/ajustar Dockerfiles e Compose.
2. O frontend consegue abrir, mas a API não é encontrada usando localhost:5000 dentro do frontend. Qual hipótese?
localhost dentro do container frontend aponta para ele mesmo. Se a API está em outro serviço Compose, use o nome do serviço e a porta interna, por exemplo http://api:5000.
3. O professor pede “prove que A fala com B”. O que é uma evidência boa?
Executar uma requisição de A para B pela rede interna e registrar a resposta/status. Melhor ainda: rota em A chama um /health de B e devolve a resposta.
4. A imagem tem 1,5 GB porque contém compilador e ferramentas de build que não são usadas em runtime. O que resolve?
Multi-stage build: usar um estágio builder com as ferramentas e copiar apenas o artefato necessário para o estágio final de runtime.
5. O container iniciou, mas a aplicação ainda não aceita conexões. Por que depends_on sozinho pode falhar?
Porque ele pode garantir apenas que o container foi iniciado, não que o processo interno esteja pronto. Um healthcheck pode fornecer um critério de prontidão.
6. Um banco perde tudo quando o container é removido. Qual recurso?
Persistência, normalmente com volume Docker.
7. Qual diagrama UML mostra melhor “Usuário → Frontend → API → Modelo → resposta”?
Diagrama de sequência, porque a pergunta é sobre a ordem temporal das mensagens entre participantes.
8. O modelo v5 foi colocado em produção com um scaler diferente do usado no treino. Qual risco?
O modelo pode receber valores em uma representação incompatível com a usada no treinamento. Pré-processamento e modelo devem ser versionados/implantados de forma compatível.
9. A distribuição das entradas mudou, mas a regra X→Y continua a mesma. Que drift?
Data drift.
10. O que diferencia um README forte de um README que apenas lista comandos?
O README forte explica problema, arquitetura, decisão, por que o recurso foi escolhido, teste executado, evidência observada e limitações.
